### 原始需求复述

用户原话：

> 「语音转文字无法使用，不仅可以自己发语音转文字，还能把好友发的语音转文字，聊天信息内容长按可以逐条转发合并转发包括语音，长按语音有转文字按钮，客户端上的功能都没有同步，查看什么问题把所有功能都同步」

拆解为 6 项增量需求（详见第 5 节需求池）：

1. 修复语音转文字不可用（根因：语音等消息类型长按事件未透传，弹不出操作菜单）。
2. 双方语音均可转文字（自己与好友语音菜单统一为「转文字」，而非「翻译」）。
3. 逐条转发（长按任意消息 → 转发 → 选择目标会话）。
4. 合并转发（多选消息 → 生成「合并转发」聊天记录卡片消息）。
5. 长按语音保留「转文字」按钮（由 1/2 自然满足）。
6. 三端功能同步（重新打包 Android/iOS/Windows，使客户端同步最新功能，属部署阶段，非本轮代码范围）。

## 2. 产品目标

1. **修复语音转文字链路**：解决语音/文件/名片/视频消息「长按/右键弹不出操作菜单」的根因，使语音消息能稳定弹出「转文字」并完成转写回填。
2. **补齐消息转发能力**：支持单条消息逐条转发，以及多选后的逐条转发与合并转发（新增合并转发聊天记录卡片），覆盖文本/图片/语音/视频/文件/名片/自定义表情全部消息类型。
3. **统一多端体验**：Web 与 Android/iOS/Windows 桌面端能力对齐，语音转文字与转发在四端行为一致。

## 3. 用户故事

1. 作为发送语音的用户，我希望长按自己发的语音能弹出「转文字」按钮并看到转写结果，这样我在不方便听语音时也能看懂内容。
2. 作为接收语音的用户，我希望长按好友发的语音同样能「转文字」，这样我不用播放就能理解对方说了什么。
3. 作为聊天用户，我希望长按任意一条消息（文本/图片/语音/视频/文件/名片/表情）都能「转发」到另一个会话，这样我能快速把内容转给他人。
4. 作为聊天用户，我希望多选多条消息后能「合并转发」成一条聊天记录卡片，这样对方能一次性看到完整上下文，而不是被刷屏。
5. 作为聊天用户，我希望点击「合并转发」卡片能查看被合并的多条消息明细，这样我能还原原始对话内容。

### 4.2 关键现状核对结论（已读代码核实）

- **长按事件根因确认**：`MessageBubble.jsx` 通过 `cloneElement(content, { onPointerDown / onPointerUp / onPointerLeave / onPointerCancel / onContextMenu })` 挂载操作手势。文本 / 图片 / 自定义表情因是原生 `div` / `button`，事件直接生效；而 `VoiceMessage / FileMessage / CardMessage / VideoMessage` 是自定义组件，组件内部只解构自己用到的 props、**未透传 rest**，导致 `cloneElement` 挂上去的手势事件没有落到根 DOM，长按 / 右键无反应 → 弹不出操作菜单 → 「转文字」不可用。
- **语音转文字链路后端已验证正常**：`useChat.transcribeVoice` → `api.voiceTranscribe`（`POST /voice/transcribe`）→ 回填 `transcript`，`VoiceMessage.jsx` 已能渲染转写结果。本轮不改后端转写逻辑，仅修前端菜单可达性。
- **好友语音菜单文案问题确认**：`ChatPage.jsx` 中 `actionMessage.sender_id === myId ? '转文字' : '翻译'`，导致好友语音显示「翻译」；后端 whisper 实际固定中文转写（language zh）。本轮统一为「转文字」。
- **转发可复用现有发送链路**：后端 `POST /conversations/:id/messages` 为通用发送入口，`ALLOWED_TYPES` 已含 `text/image/sticker/card/voice/video/file`；转发本质是「复制原消息 type + content 到目标会话发一条新消息」。媒体类消息的 `content` 为 `/uploads/...` 地址，转发直接复用该地址、不重新上传。
- **各类型 content 校验约束（转发须携带对应字段）**：`voice` 需 `voice_duration ∈ 1..60`；`video` 需 `video_duration ≥ 0`；`file` 需 `file_name`（非空 ≤255）+ `file_size`（正整数）；`card` 的 content 为 JSON（服务端会重新校验并回填 nickname/avatar_url）。转发生成 payload 时需从原消息补齐上述字段。
- **merged 类型为新增**：`ALLOWED_TYPES` 与 `normalizePayload` 均无 `merged` 分支；`messages.content` 为 `TEXT NOT NULL DEFAULT ''`，可承载 merged 的 JSON 内容，**无需新增数据库列**（`serializeMessage` 已对 content 原样透传）。
- **merged 的前端渲染/摘要需补齐**：`MessageBubble.jsx` 的「非文本类型」排除列表未含 merged，会误走文本渲染；`lib/format.js` 的 `summarizeLastMessage` 默认分支会把 merged 的 JSON 原文显示在会话列表摘要。
- **多选态当前不存在**：需新增 UI 状态（建议放 `ChatPage` 局部 state），并新增底部操作栏（逐条转发 / 合并转发，删除/收藏可选）。

## 5. 需求池（P0 / P1 / P2）

### P0 —— 必须实现

#### 需求 1：修复语音 / 文件 / 名片 / 视频消息长按事件未透传（语音转文字根因）

- **涉及（修改）**：`web/src/components/VoiceMessage.jsx`、`FileMessage.jsx`、`CardMessage.jsx`、`VideoMessage.jsx`（接受并透传 `MessageBubble` 通过 `cloneElement` 注入的 `onPointerDown/onPointerUp/onPointerLeave/onPointerCancel/onContextMenu` 到各自根 DOM 元素）；复核 `MessageBubble.jsx` 的挂载逻辑保持兼容。
- **现状**：上述 4 个组件只解构自身用到的 props，未透传 `rest`，导致长按/右键手势事件丢失、弹不出操作菜单。
- **验收标准**：
  - 长按语音 / 文件 / 名片 / 视频消息，均能弹出消息操作菜单（与文本 / 图片 / 表情行为一致）。
  - 桌面端右键上述消息类型，同样能弹出操作菜单。
  - 长按语音消息时，菜单中可见「转文字」按钮（文案见需求 2）。
  - 不影响各消息类型自身点击行为：语音播放/暂停、文件下载、名片查看、视频播放/首帧点击。

#### 需求 2：双方语音均可「转文字」（菜单文案统一）

- **涉及（修改）**：`web/src/pages/ChatPage.jsx`（语音消息菜单按钮文案，由 `sender_id === myId ? '转文字' : '翻译'` 统一为「转文字」）。
- **现状**：好友语音长按菜单显示「翻译」，但后端转写实际固定中文。
- **验收标准**：
  - 自己与好友发送的语音消息，长按菜单均显示「转文字」，不再出现「翻译」。
  - 点击后复用现有 `transcribeVoice` → `POST /voice/transcribe` 流程，转写结果回填并在气泡内展示（含「转写中…」加载态与「复制」按钮）。
  - 转写失败有 Toast 提示；转写结果文案为中文（language 固定 zh）。

#### 需求 3：逐条转发（单条消息转发到目标会话）

- **涉及（修改 + 新增）**：
  - 修改 `web/src/pages/ChatPage.jsx`：长按操作菜单新增「转发」按钮。
  - 新增「选择目标会话」弹层（复用当前会话列表 `conversations`，展示单聊 + 群聊，我参与的会话）。
  - 新增 `useChat.forwardMessage(conversationId, message)`：把原消息的 `type + content`（并按类型补齐 `voice_duration / video_duration / file_name / file_size`）作为新消息发送到目标会话。
  - 后端复用 `POST /conversations/:id/messages`，无需新增接口。
- **现状**：无转发能力；`_send` / `api.sendMessage` 通用发送入口已具备。
- **验收标准**：
  - 长按任意类型消息（text/image/sticker/card/voice/video/file），菜单出现「转发」。
  - 点击「转发」→ 弹出会话选择列表 → 选择目标会话后，将该消息作为一条**新消息**发送到目标会话。
  - 转发消息的 `sender_id` 为当前用户（不保留原发送者身份）。
  - 媒体消息（image/video/voice/file/sticker/card）复用原 `/uploads` 地址、不重新上传；语音带 `voice_duration`、视频带 `video_duration`、文件带 `file_name` + `file_size`、名片复用原 content JSON（服务端重新校验回填）。
  - 目标会话为只读（单聊已非好友）时禁止转发并给出提示；发送成功有 Toast 反馈，目标会话摘要 / 未读正常更新。

#### 需求 4：合并转发 + 多选态 + 新增 merged 消息类型

- **涉及（新增 + 修改）**：
  - 后端 `server/lib/messages.js`：`ALLOWED_TYPES` 与 `normalizePayload` 新增 `merged` 分支（校验 content 为合法 JSON 结构），序列化/广播链路放行。
  - 前端 `web/src/components/MessageBubble.jsx`：新增 `merged` 渲染分支（识别 `isMerged`，避免误走文本渲染）。
  - 新增 `web/src/components/MergedMessage.jsx`：「合并转发」聊天记录卡片（标题 + 摘要），点击打开明细。
  - 新增「合并转发明细」只读视图（复用 `MessageBubble` 渲染被合并的消息列表）。
  - 修改 `web/src/pages/ChatPage.jsx`：新增多选态（勾选框 + 底部操作栏「逐条转发 / 合并转发」，删除/收藏可选见 P1/P2）。
  - 修改 `web/src/lib/format.js`：`summarizeLastMessage` 新增 `merged → '[聊天记录]'`。
  - 新增 `useChat.forwardMessages`（合并转发）与逐条转发复用方法。
- **现状**：无多选态、无 `merged` 类型；`content` 列可承载 JSON，无需新增数据库列。
- **验收标准（合并转发）**：

  - 点击卡片可查看被合并消息明细（只读，逐条复用现有气泡渲染）。
  - 合并转发消息的 `sender_id` 为当前用户（不保留原发送者身份）。
  - 合并转发消息在会话列表摘要显示为 `[聊天记录]`。
  - 后端放行 `merged` 类型并正确序列化 / 广播，socket `message:new` 正常送达四端。
- **验收标准（多选态）**：

  - 多选态有明确退出方式（见待确认问题），退出后恢复普通聊天态。

## 6. UI / 交互说明

### 6.1 长按操作菜单（需求 1 / 2 / 3 / 5）

- 长按任意消息弹出底部操作菜单（现有 `Modal`），项顺序建议：**转发 → 多选 → 收藏 →（语音时）转文字 → 撤回 → 取消**。
- 「转发」：单条消息直接进入「选择目标会话」。
- 「多选」：进入多选态（见 6.2）。
- 「转文字」：仅语音消息显示，自己与好友均显示「转文字」。
- 「撤回」：保留现有权限与 2 分钟时间窗逻辑不变。

### 6.2 多选态（需求 4 / 7 / 8）

- 从长按菜单「多选」进入多选态：每条消息左侧/气泡前出现勾选框，点气泡本身 = 勾选/取消勾选。
- 底部操作栏替换输入区（或覆盖在输入区上方），包含：**逐条转发 / 合并转发**（P1/P2 追加：删除 / 收藏）。
- 退出方式：右上角「取消」/「完成」，或返回键；退出后清空勾选并恢复聊天态。

### 6.3 选择目标会话（需求 3 / 4）

- 「转发」「逐条转发」「合并转发」共用同一个「选择目标会话」弹层。
- 弹层展示我参与的会话列表（单聊显示对方昵称/备注，群聊显示群名），支持搜索过滤；点击即发送并关闭。
- 只读会话（单聊已非好友）置灰或不可选。

### 6.4 合并转发卡片与明细（需求 4）

- 合并卡片展示：标题（如「某某的聊天记录」）+ 摘要（被合并消息的 N 条摘要，如「[文本][图片][语音]」）+ 卡片样式（区别于普通气泡）。
- 点击卡片 → 打开只读明细视图（弹层或新路由），逐条复用 `MessageBubble` 渲染被合并消息；明细内不提供长按操作。
- 会话列表摘要显示 `[聊天记录]`。

## 7. 待确认问题

1. **合并转发卡片点击后的展示形态**：是只读弹层（推荐，复用 `MessageBubble`）还是独立页面/新路由？建议只读弹层，避免增加路由复杂度。
2. **多选态的进入/退出方式**：是「长按菜单里点『多选』进入」，还是「长按直接进入多选态」？退出是否统一用右上角「取消」+ 返回键？建议：长按菜单保留单条操作并新增「多选」入口。
3. **逐条转发是否保留原发送者身份**：本 PRD 按「不保留，转发为新消息，sender_id = 当前用户」设计（与微信一致）。是否需要在卡片/气泡上标注「转发自 xxx」？
4. **合并转发是否计入消息搜索 / 聊天记录类型筛选**：建议计入并显示为 `[聊天记录]`（列为 P1）。是否要把被合并消息的文本内容也纳入关键词检索？
5. **merged 消息 content 的 JSON 结构与上限**：被合并消息条数上限（建议单次 ≤ 100 条）、摘要截断规则、content 总长度上限（`TEXT` 字段无硬限，需应用层约束）。参考微信合并转发上限。
6. **合并转发的「原始会话信息」与跨会话转发**：从单聊转发到群聊 / 从群聊转发到单聊时，卡片标题取谁的名字？是否在卡片上展示原始发送者昵称与原始会话名？
7. **多选「删除」的语义**：是「本地删除（仅自己视图移除，不同步对方）」还是「复用撤回（同步双方）」？是否允许删除他人消息（仅群主/管理员）？
8. **合并卡片内被合并消息的失效处理**：若原消息后续被撤回/删除，卡片明细是「快照冻结」还是「实时反映撤回」？建议快照冻结（转发时写入 content）。
9. **语音转文字语言**：确认好友语音与本人语音均固定中文转写（language=zh），不实现真正的「翻译成中文」。本 PRD 已按固定 zh 处理。
10. **转发到群聊时 @ 信息处理**：文本消息转发是否保留原 `mentions`？建议不保留（转发为纯文本，避免误 @ 新群成员）。
